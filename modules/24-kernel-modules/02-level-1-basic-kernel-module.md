## ⭐ Level 1: Basic — Kernel Module Basics

![Linux kernel architecture — subsystems and module interfaces](https://upload.wikimedia.org/wikipedia/commons/1/1c/Linux_kernel_diagram.svg)

*Linux kernel architecture showing subsystem layout (Wikimedia Commons / public domain)*

> **Level 1 Goal:** Understand what kernel modules are, how to list loaded modules, and how to get detailed information about specific modules.

### What You'll Cover
- What kernel modules are: drivers, filesystems, and networking code
- Listing loaded modules with `lsmod` and understanding the output
- Getting module info with `modinfo`: author, license, parameters, dependencies
- Where modules live: `/lib/modules/$(uname -r)/`
- Module auto-loading via udev and `/etc/modules-load.d/`

Kernel modules are dynamically loadable pieces of code that extend the kernel without rebooting. Unlike monolithic kernels where everything is compiled in, Linux lets you add or remove drivers, filesystem implementations, and network protocols on the fly.

At this level you will learn:

- **lsmod** output: The `Used by` column shows reference counts. A module with a non-zero count cannot be safely removed. The output reads `/proc/modules` internally.
- **modinfo**: Shows the module's filename, license (GPL, proprietary, etc.), author, description, dependencies (alias), and tunable parameters. Use `modinfo -p module_name` to list only parameters.
- **Module storage**: `/lib/modules/$(uname -r)/kernel/` contains compiled `.ko` files organized by subsystem (`drivers/`, `fs/`, `net/`). The `modules.dep` file maps dependencies and is generated by `depmod`.
- **Auto-loading**: udev triggers module loads when hardware is detected. Systemd reads `/etc/modules-load.d/*.conf` at boot to load modules that have no hardware trigger (e.g., `ip_tables`).
